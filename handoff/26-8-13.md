## 特性一：受限文章实时计数

### 上一轮的结论是错的

`handoff/26-8-12.md` 的「只读接口调查结论：不存在」错在两处：

1. 用的 header 是 `x-luogu-type: content-only`，而本仓库自己在
   `src/features/ide-batch/feature.js` 和 `hidden-intro` 里用的是
   **`x-lentille-request: content-only`**（`ide-batch/feature.js:78` 还专门注释了旧写法已死）。
2. 只试了文章**页面路径**，没试**列表路径**。而 `POST article.vote` 能通本身就说明
   WAF 拦的是页面路径、不是所有路径。

### 一手实测

| 请求（均带登录态） | 结果 |
|---|---|
| `GET /article/2l4x53kj` + `x-lentille-request: content-only` | 拦截页，2528B，含「安全访问中心」 |
| `GET /article/2l4x53kj?_contentOnly=1` | 同上 |
| `GET /article/2l4x53kj/replies` | **200 `application/json`**，`{replySlice:[...]}`，10548B |
| `GET /user/697932/article` + 同 header | **200 JSON**，目标受限文章就在列表里 |

### 契约

```
GET /user/{authorUid}/article?page={N}
Header: x-lentille-request: content-only
→ data.articles = { perPage: 10, count: <总数>, result: [ … ] }
→ result[i] = { lid, title, category, time, author, upvote, replyCount,
                favorCount, status, solutionFor, promoteStatus, collection,
                content }      ← content 截断到 128 字
```

证据：`2l4x53kj` → `upvote: 24`、`favorCount: 22`、`replyCount: 50`。
**`upvote: 24` 与 owner 真机点赞实测的真值 24 完全一致**
（点赞后 25、撤回后 24）。同一时刻保存站快照是 19 / 17
（`updatedAt: 2026-08-12T13:31:01.000Z`）。

### 落地算法

1. 保存站 `query` → `authorId`（首屏照旧用保存站渲染，**不阻塞**）
2. `GET /user/{authorId}/article?page=1` → 拿 `count`，顺便碰第一页
3. 未命中 → 剩余 `ceil(count/perPage)-1` 页**并行**拉，扁平找 `lid`
4. 命中 → 用真值替换计数，作为后续写响应增量的**基线**
5. 未命中 → 回落保存站快照

端到端实测：**637 ms、第 1 页命中、排序稳定**（同一 page 连续两次请求的 lid 序列一致）。

### 边界，逐条实测过

- **列表不按时间排序**：page1 时间区间 `[1759309175, 1754987571]`，page2 是
  `[1776079628, 1773115485]`（比 page1 新），页内也非降序 → **不能二分，只能扫**。
- `perPage` 固定 10，`?perPage=50` 无效（返回仍是 10 条）。
- 防爆：作者 200 篇 = 20 页。先试第 1 页 + **缓存 `lid → page`**，未命中再并行拉并设
  上限（建议 ≤10 页），超限回落保存站。
- `content` 截断到 128 字 → **正文仍然只能靠保存站**。
- 列表**不含 `voted` / `favored`** → 个人状态仍靠 `canary.7` 的持久层，那部分不动。
- ★ 实现警告：**不要把这批数据当 `archived` 源整体喂进
  `completeRestrictedArticleInteraction`**。该函数的 `archivedBoolean` 会原样接受
  `false`，而列表压根没有个人状态字段 —— 只允许覆盖 `upvote` / `favorCount` /
  `replyCount`，个人状态一个字节都不能从这里来。
- 页面 CSP **挡死页面内直连 `api.luogu.me`**（实测 `Failed to fetch`）→ 保存站必须继续
  走 `GM_xmlhttpRequest`，这已是现状。

### 附带红利：实时评论

`GET /article/{lid}/replies` 对受限文章也返回 200 JSON `{replySlice}`，
说明「实时评论优先、保存站回退」这条路是真的通的，保存站评论（6 小时 TTL）
可以真正降级为兜底。

## 特性二：hover 预览卡

owner 拍板范围：

- 题目卡 = 基础（题名 / 难度 / 通过率）+ 标签（**默认折叠**，标签会剧透算法）+ 我的状态（含**上次尝试**）
- 用户卡 = 基础 + 荣誉 + 比赛 Elo + 关系与轨迹；**热力图不做**；**✅ 和气球要显示**
- 触发范围：**悬停用户名和头像都出卡**

### 题目卡字段与来源

来源 A：`GET /problem/{pid}` + `x-lentille-request: content-only`

| 字段 | 路径 | 实证 |
|---|---|---|
| 题名 | `data.problem.name` | ✅ |
| 难度 | `data.problem.difficulty`（数字） | ✅ P3372=4、P1000=1；沿用现有 9 档映射表 |
| 通过率 | `totalAccepted / totalSubmit` | ✅ P3372 = 259644 / 636915 |
| 我通过了没 | `data.problem.accepted` / `.submitted`（布尔） | ✅ **反证过**：P3372/P1001 = false，B3836 = **true** |
| 我的最高分 | `data.problem.score` / `.bestRecord` | ✅ B3836 → `score: 100`、`bestRecord: {id:179363526, score:100, status:12, enableO2:true}` → 能直接链到那条记录 |
| 我收藏了没 | `data.bookmarked` | ✅ |
| 时限 / 内存 | `data.problem.limits` | ✅ P3372 `time[0] = 1000` |
| 官方相似题 | `data.recommendations` | ✅ 5 条 `{pid,name,difficulty,submitted,accepted}`（B3836 为 0 条，入门题没有） |

来源 B：`GET /_lfe/tags` → `{tags, types, version}`，`tags[i] = {id, name, type, parent}`，
32389B。`problem.tags` 是数字 id 数组（P3372 = `[42, 523]`），**必须配这张字典**。
字典带 `version`，可长缓存。

来源 C：`GET /record/list?user={uid}&pid={pid}` —— ★ **这是旧版页面，不吃
`x-lentille-request`**，数据在 `_feInjection.currentData.records`，整页仅 4234B。

```
row = { id, score, status, submitTime, time, memory, language,
        sourceCodeLength, enableO2, problem, contest, user }
```

证据：B3836 → `score: 100`、`submitTime: 1727831949`、`time: 73`(ms)、
`memory: 680`(KB)、`id: 179363526`。

★ **坑**：`problem detail` 的 `data.lastCodeAt` 与这个 `submitTime` **数值恰好相同**
（都是 1727831949），但语义不同 —— `lastCodeAt` 是 IDE 里最后保存代码的时间，
不是最后一次提交。**「上次尝试」必须用 `record/list`，不能图省事读 `lastCodeAt`。**

成本：`problem detail` 体积随题面浮动，P3372 = 11787B、**P1001 = 35550B**。
批量兜底 `GET /problem/list?keyword={pid}` 固定 24733B 且带
`name/difficulty/tags/totalSubmit/totalAccepted/submitted/accepted`，
但**拿不到** `score` / `bestRecord` / `limits` / `bookmarked` / `recommendations`。
→ 建议 hover 停留 ~300ms 才发请求，并按 pid 缓存。

### 关注按钮：写契约

```
POST /api/user/updateRelationShip          ← 注意 Ship 的 S 大写；同源，无 query
Content-Type: application/json
X-CSRF-TOKEN: <取自 meta[name=csrf-token]>
X-Requested-With: XMLHttpRequest

{"uid": 116524, "relationship": 1}         ← 1 = 关注，0 = 取消
→ 200 {"_empty":true}
```

★ **响应体不回传新状态** —— 与 `article.favor` 完全同款：客户端自行 toggle
`userRelationship` 并 `followerCount ± 1`。**卡上的按钮必须自己维护状态，
且写失败要回滚**，这和已经踩过的收藏计数是同一个坑。

枚举语义：`0` = 未关注、`1` = 已关注（`reverseUserRelationship: 1` 直接证实
「他关注了我」）。**没有独立的枚举字典端点** —— `/_lfe/relationships`、`/_lfe/dicts`、
`/_lfe/enums` 全部 404，只有 `/_lfe/tags` 是 200；洛谷前端把未知值兜底成 `Unrelated`。
→ **遇到 0/1 之外的值（如黑名单）应降级为不显示按钮。**

按钮文案实测：未关注 →「关注」；我关注 + 他也关注我 →「**互相关注**」。

### 60 篇上限：根除不了，但已大幅缓解

先证明根除不了 —— .cn 上**没有单篇文章的只读接口**：

| 试探 | 结果 |
|---|---|
| `GET /api/article/{lid}` | **404** |
| `GET /api/feed/list?user={uid}` | 200 但**不含任何计数** |
| `GET /article/{lid}/replies` | 200 但只有 `replySlice`，无文章元数据 |
| 列表 `orderBy` / `sort` / `order` / `sortBy` | 全部不改变结果集 → **不能二分** |
| 列表 `?keyword=` | **无效**（26 篇原样返回） |

另外实测确认页内 `promoteStatus` / `category` / `time` 三者都乱序，
之前以为的「page2/3 时间降序」是巧合，排序不可利用。

三招缓解：

1. **`?category=N` 过滤** —— 实测生效（作者 697932：26 篇 → category=3 只剩 4 篇，
   3 页变 1 页）。保存站存档里就带 `category`。分类过期（文章被改分类）自动退回全量扫。
2. **页数上限 6 → 40**（覆盖 400 篇），**并发限 5 分批**发。
3. **2500ms 时间预算**兜底，超了回落保存站并在 console 报截断。

净效果：常见作者 1 次请求命中；只有**单个分类超过 400 篇**才会回落。
