## ★ 三个版本才收敛：两个隐藏缺陷是怎么暴露的

`canary.5` 的状态模型本身是对的，但用户验收仍然失败。后续两轮定位到两个真实缺陷：

### 1. 传输层包装打错了 window（canary.6 修复）

在 owner 的 Edge 上实测：Tampermonkey 报告 `GM_info.sandboxMode === "raw"`，
但 **`window !== unsafeWindow`** —— 只要用了 `@grant`（本脚本需要 `GM_xmlhttpRequest`），
脚本拿到的 `window` 仍是 TM 的沙箱作用域对象，`unsafeWindow` 才是页面主世界。

LuoguSP 把 `fetch` / `XMLHttpRequest` 的包装打在了脚本自己的 `window` 上。
`document.write` 走的是**共享 DOM**，所以页面照常重建、按钮照常出现；
但官方前端在主世界发出的写请求根本不经过包装器 —— **完全静默**，
外观与「功能没做」一模一样。同一根因下**保存站评论回退在 canary.5 也是坏的**。

判据（从页面主世界看）：`__LUOGUSP_CDN_RUNTIME__ === null`、`XMLHttpRequest` 与
`fetch` 均为 `[native code]`，同时 LuoguSP 的 DOM 产物存在。

修法 `src/features/restricted-content/transport-realm.js`：显式选中页面 realm，
且 `Response / URL / Request / Headers` **必须取自同一 realm**
（跨 realm 的 `new Request(pageRequest, init)` 会失败、`instanceof` 会假阴性）。
页面 realm 不可用时回退脚本 `window`，而不是装一个半坏的传输层。

★ **教训：Playwright QA 用 `addInitScript` 注入的是主世界**，天然满足了真实环境
不满足的前提，全绿而毫无价值。用户脚本的验证不能只靠 Playwright。

### 2. 未确认的计数被伪造成 0（canary.7 修复）

`Number(null) === 0` 且 `Number.isFinite(0)` 为真。持久层只判 `isFinite`，
于是「未确认」的 `upvote` / `favorCount` 被规范化成 `0` 写进记录，
再按「已确认计数优先」的规则**反过来盖掉保存站的真实值**。
真实浏览器里的表现：点赞并刷新后，收藏计数从 17 变成 0，按钮文字退化成「收藏」。

修法：`store` 与 `tracker` 统一用 `countOrNull`（显式排除 `null` / `undefined` / `""`）；
存储键升到 `luogusp.article-interaction.v2`，让 canary.6 写下的脏记录自动失效。

## 本轮修复了什么

### 根因

「公共存档快照」和「账号实时状态」此前被当作同一数据源：每次引导受限文章页都用保存站的
`upvote` / `favorCount` 重建 `lentille-context`，而保存站根本不返回 `favored` / `voted`，
于是刷新后个人状态永远回到 `null`，官方组件据此把下一次点击当成「新增收藏 / 新增点赞」，
用户无法撤回。

### 官方契约（一手证据）

读源码确认，不是猜的 —— columba `20260730-2078` 的 `article.show` 组件
（`columba~0bd2df6a7ee2b996.js`）：

- 收藏：`POST article.favor`，已收藏时带 `?remove=1`；**响应体不参与状态**，
  组件自行 `favored = !favored`、`favorCount ± 1`。
- 点赞：先算 `vote = (article.voted === intent ? 0 : intent)`，`POST article.vote?vote=<vote>`，
  再用响应体 `{upvotes, voted}` 覆盖 `article.upvote` / `article.voted`。
- 状态容器是 `lentille current data`（即 `lentille-context` 的 `data`），组件直接改它。
- 官方前端用 axios，`adapter: ["xhr","http","fetch"]` → **写请求实际走 XMLHttpRequest**，
  不是 fetch。观察写响应必须挂在 XHR 层。

### 只读接口调查结论：不存在

`GET https://www.luogu.com.cn/article/{lid}`、加 `x-luogu-type: content-only`、
加 `?_contentOnly=1` 三种形式全部返回「安全访问中心」拦截页（HTTP 200 + HTML，2680 字节）。
受限文章没有任何可带当前 `.cn` 登录态读回 `favored` / `voted` 的同源只读接口，
保存站也不提供。因此个人状态只能来自官方写响应，按账号隔离持久化。

### 实现

| 文件 | 职责 |
|---|---|
| `src/features/restricted-content/article-write-observer.js` | 纯函数：把一次「官方写请求 + 响应」翻译成已确认状态。非 2xx 一律返回 `null`。 |
| `src/features/restricted-content/article-interaction-store.js` | 按 `UID:文章ID` 隔离的持久层（`localStorage` 键 `luogusp.article-interaction.v2`），30 天 TTL、200 条上限、损坏负载可恢复、无存储时降级。 |
| `src/features/restricted-content/article-interaction-tracker.js` | 运行时胶水：持有当前显示值、观察写入、落盘；`prepareRestrictedArticleInteraction` 是引导页的单一入口。 |
| `src/features/restricted-content/article-interaction-state.js` | 三来源合并：确认状态 > 保存站快照 > `null`。公共计数按新鲜度取舍，个人状态永不被保存站覆盖。 |
| `src/features/restricted-content/reply-xhr-adapter.js` | 新增 `onWrite`：只旁观已完成的写请求，不改方法/URL/请求头/请求体/响应。 |
| `src/features/restricted-content/article-write-adapter.js` | fetch 侧的同契约镜像（读响应副本），防官方前端日后换 adapter。 |

优先级与新鲜度规则：

- `voted` / `favored`：只认已确认记录；保存站永远不提供，未知就是 `null`，**不伪造 `false`**。
- `upvote` / `favorCount`：保存站 `updatedAt` 比确认记录新才允许覆盖计数；否则用确认值。
- 匿名访客既不读也不写持久记录；换账号读不到上一个账号的状态。
- 写失败（非 2xx）不更新内存状态、不落盘，官方组件本身也不做乐观更新。

## ★ 顺手修掉的一个真实隐患：工作区 CRLF 漂移

`cdn/releases/2.13.5/` 与 `cdn/releases/2.13.5-canary.20/` 共 **34 个已发布产物**在工作区被
展开成了 CRLF。git 因为 `.gitattributes` 的 `text=auto` 归一化而**报告工作区干净**，
但 `scripts/cdn/prepare.mjs` 是逐字节从工作区拷贝上传的 —— 从这个状态发布会让每一个已安装
`2.13.5` 的用户的 `@require` SHA-256 校验失败，脚本当场加载不出来。

- 发现方式：发布前的不可变性门禁直接拦下（`Refusing to deploy: 32 CDN artifact(s) ...`）。
- 处理：逐文件用 `git show :<path>` 的索引字节（LF）写回工作区，随后校验
  磁盘字节与 `HEAD` **逐字节一致（0 处不符）**，并抽查远端 `2.13.5` 产物哈希与本地相同 ——
  说明 CDN 从未被污染，只有本地工作区漂移过。
- 遗留：Windows 上 `core.autocrlf=true` 与仓库 `.gitattributes` 的 `eol=lf` 仍会打架，
  某些操作（检出、切分支、外部工具改写）可能再次把这些文件展开成 CRLF。
  **每次发布前都依赖这道门禁，不要绕过它。** 想根治可以把本仓库的
  `core.autocrlf` 设为 `false`（`git config core.autocrlf false` 后重新检出 `cdn/releases`）。

## 用户验收要做的事

装上 `canary/LuoguSP-canary.user.js`（★ 安装脚本没有 @updateURL，油猴**不会自动更新**，必须覆盖安装到 `2.14.0-canary.7`），
用真实账号在一篇受限文章上依次确认：

1. 点赞 → 计数变为洛谷真实值，按钮高亮。
2. **刷新页面** → 仍然高亮、仍然是真实计数（不回跳到保存站旧值）。
3. 再点一次点赞 → 成功撤回（走 `vote=0`）。
4. 收藏 / 取消收藏重复上述三步（走 `favor` 与 `favor?remove=1`）。
5. 退出登录或换账号打开同一篇文章 → 不应显示上一个账号的收藏/点赞状态。

### 已知局限（不是缺陷）

- 首次打开时的点赞/收藏数仍来自保存站存档快照，可能与洛谷真实值差很多；
  写入成功后才会被服务器确认值取代，之后刷新就稳定了。受限页没有实时只读接口，
  这个首屏差异无法消除，只能靠「申请更新」刷新存档（已带 `forceUpdate: true`）。
- 收藏计数没有服务器确认值可用（官方响应体不带），沿用官方组件同款 ±1 推导，
  只是额外做了不小于 0 的钳制。
